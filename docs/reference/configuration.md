# Static configuration reference

Generated by `bigbrotr config reference` from the same Rust registry used by the parser and JSON Schema.

This initial schema resolves candidate roots, selected roles and resource arithmetic. It does not activate managed/declarative authority, open engines, establish ownership or enable runtime services. Remaining service-specific settings and adapters are explicit implementation work; unknown keys fail. `doctor` returns exit 4 while live authority/adapter checks are unavailable.

Use `bigbrotr config init --recipe full --output instance.toml`, then `config validate --file instance.toml` or `config show --file instance.toml`. Initialization creates candidate IDs and refuses any existing output path. A copied ID is not an ownership grant. Fixed examples contain reserved `.example` destinations and need operator enrollment before future acquisition.

`validate` is offline and never resolves secret references. `show` is a diagnostic document, not a round-trippable configuration: byte values and durations are normalized to bytes/microseconds and unsigned integers are decimal strings. Dependent defaults identify their source key and any microsecond offset; monitor stored checks follow the chosen computed set, and the default API timeout follows the read timeout plus 5s. Secret references and relay path/query values are redacted. Structured revisit bands use start_age/end_age/cadence with explicit durations, ordered nonoverlapping intervals and a positive cadence; their normalized diagnostic durations are decimal microseconds. Desired/applied revisions stay null until Control exists. The initial_policy metadata identifies the complete current non-root policy seed: normalized defaults and staged settings, compact JSON and its PostgreSQL 16.15 JSONB text rendering each bounded to 10MiB, a domain-separated SHA-256, byte length and setting count. Roots and secret references are excluded; this candidate digest grants no authority and never replaces accepted policy at restart. Fractions normalize signed zero. The raw source-file digest remains distinct; comments and equivalent units may change it without changing the policy seed. No environment override stack is read.

`config inspect --file instance.toml` explicitly reads PostgreSQL Control using the protected application credential. It compares the file with the accepted configuration, validates its closed stored document/digest against current roots, and reports redacted accepted values. Managed file policy is unused initialization input; declarative changes remain staged. The observation grants no authority and applied_revision stays null. Missing dataset/configuration returns exit 4; unavailable, incompatible or wrong-deployment Control fails. A valid static root is required before connection. No database initialization or policy activation is performed.

`config initialize --file instance.toml` explicitly accepts a statically validated policy once into empty Control after migration 0801. It uses the protected application credential with narrow SQL grants, records an installation actor and immutable audit receipt, and preserves existing accepted state. No human enrollment, security policy or runtime grant is created. A lost COMMIT is outcome-unknown (exit 4); retry the same dataset/instance to resolve the serialized receipt. Wrong, incomplete or unattributed existing state is refused. See [configuration/runtime](../engineering/configuration-and-runtime.md#explicit-initial-control-acceptance) for the boundary.

`config activate-initial --file instance.toml --request-id HEX32 --expected-revision 1` explicitly snapshots the validated accepted policy as security revision 1 after migration 0802. It refuses any previous runtime history and atomically records the policy head, audit and idempotent command receipt. Managed seed drift is unused; declarative normalized drift is refused. It does not grant a runtime lease. Exit 4 means COMMIT outcome unknown: retry the same ID and expected revision to resolve the receipt. See [the first security revision](../specification/operations-contract.md#explicit-first-security-revision).

A selected local Archive requires explicit archive.catalog_id: a nonzero lowercase 128-bit hexadecimal installation identity. config init generates it alongside fresh instance/dataset IDs; examples use a deterministic candidate. It is a deployment root excluded from the persisted policy seed. Older selected-Archive files must add the actual expected catalog ID; copying an observed row is not verification. Unselected catalogs may omit the ID, but staged IDs still require valid syntax.

`archive inspect --file instance.toml` uses the protected postgres.catalog manager credential and this expected dataset/catalog/root binding to verify installed commit guards and logical scientific schema metadata. It grants no runtime authority, initializes nothing and does not check data-file contents. See [catalog inspection](../engineering/configuration-and-runtime.md#explicit-catalog-inspection).

Selected Archive may stage separate postgres.catalog.read_user and read_password_ref deployment roots. They must be paired when Archive is local, use a different login from the manager, and remain outside policy bytes. Offline validation checks syntax only. Explicit archive.reader.enabled (default false, restart required) selects the private grant allocation reader and requires local Control/Archive plus both reader credentials; it does not enable publication or alter stored policy bytes. Its native HTTP qualification is tracked under P08-T02. The explicit `archive receipt-inspect` command requires both, checks actual reader privileges and observes retained inputs through a fresh native process; absence grants no replay or source protection. See [receipt inspection](../user/archive-receipts.md).

Optional clickhouse.initialize_user and initialize_password_ref must be paired when staged. They are deployment roots excluded from policy bytes, remain staged-unselected for ordinary runtime, and are selected only by explicit Index initialization. The initializer must not be default or either configured read/write login; no other credential is used as a fallback. Ordinary writers receive no DDL authority. The password reference uses the protected file reader and stays redacted; offline commands do not open it. See [protected local credentials](../security/credentials.md) for the operator configuration.

Paired optional export.destination.id/root are deployment-owned and excluded from policy bytes. Offline validation checks their syntax and separation from selected writable stores without reading files. The finite `export destination-initialize --file instance.toml` binds an existing private empty root explicitly; `export destination-inspect` reopens it without creation or repair. Neither command authorizes or executes an export job. See [export destinations](../operations/export.md).

Optional read.cursor.keyring_ref is a protected-file deployment root, redacted and excluded from accepted policy bytes. Offline commands validate syntax only. The explicit `access cursor-keyring prepare --file instance.toml` prepares local keys in an existing dedicated mode0700 directory; `access cursor-keyring inspect` reads an existing final file. Neither contacts Control or activates a cursor key. See [protected local credentials](../security/credentials.md) for preparation, staging and recovery boundaries.

Storage-root alias comparison removes repeated separators and trailing slashes. A selected local Archive additionally follows the native catalog identity rules: absolute path other than /, no repeated separators or glob characters (*, ?, [), and at most 4096 bytes including its terminal slash. A missing terminal slash is added only for catalog binding; configured paths otherwise stay intact. Filesystem links and mounts remain runtime checks.

Secret references require `file:/absolute/filename` with a final filename, no dot components or trailing slash, and at most 8192 bytes including `file:`. Credential consumers require a regular file owned by the effective process UID, POSIX mode exactly `0400` or `0600`, and no symlink in any path component. Secret bytes are preserved exactly, including a trailing newline; adapters own text/key semantics. These constraints do not certify filesystem ACLs or promise memory zeroization. Offline configuration commands validate only reference syntax; they do not check ownership, permissions or contents. See [protected local credentials](../security/credentials.md) for mount and runtime limits.

Static validation checks the declaration, not live engine versions, TLS certificates, permissions, filesystem aliases, accepted-work drain capacity or measured memory. Limits are checked with u64 arithmetic; complete signed events remain invariant. JSON Schema documents shapes while the CLI enforces semantic relationships.

Exit codes: 0 requested output/static success, 1 I/O, 2 usage, 3 invalid configuration, 4 incomplete doctor checks. Input is a regular UTF-8 TOML file bounded to 10MiB, with the upstream parser's recursion bound. Values are not echoed in parse errors.

Missing static contracts remain explicit P01-T04 work: structured auth bindings, observer allocation, directory sources, Geo sources, collection selectors, import scope/source shape, retention/maintenance plans, archive backend/provider roots and detailed derivation/ranking/read exposure/signing/publication/gateway policies. Cadence/resource templates for Deriver, Ranker and export do not implement target/profile/seed selection or finite export commands. Only the keys below are accepted; unsupported feature enablement is refused. No P01-T04 completion is claimed.

The single current persisted policy format is bigbrotr-product-policy/3, with schema metadata3 and its matching digest domain. Superseded formats1/2 and incomplete current documents are refused; no missing-key backfill or candidate projection is applied. Historical evidence stays bound to its recorded source. Populated upgrades remain separate implementation work. relay_policy.banned defaults to an empty array, accepts at most 100000 closed endpoint-or-host records before normalization and deduplication, and is redacted in diagnostics. Endpoint bans match the complete normalized URL; host bans match one exact normalized DNS or bracketed IP host across schemes, ports and paths, without subdomain, wildcard, alias or resolved-address expansion. IPv4-mapped host literals compare as IPv4 without changing endpoint identity. ingest.request_receipt_retention accepts1..64, default64, independently of the outstanding window. The first OPEN-prefix profile captures it from both exact accepted startup documents and preserves stop/recovery on accepted policy change. Its planned Live reload metadata does not implement Live adoption. See [configuration/runtime](../engineering/configuration-and-runtime.md#acquisition-ban-policy-document-extension).

network.private.rules defaults to an empty array and is a deployment-locked private destination ceiling requiring controlled restart. At most 256 closed records contain exactly endpoint or hostname, cidr and integer port in 1..65535. The existing ws/wss normalizer preserves endpoint path/query; hostnames require normalized ASCII DNS syntax without wildcards, IP literals or overlay suffixes. The shared direct-route validator checks CIDR host bits and endpoint port agreement. Duplicates consume the limit. All rules are redacted in diagnostics, validated even without acquisition, and excluded from persisted policy bytes. They create no enrollment, reader permission, publication eligibility or dial grant. Acquisition must intersect the selected enrolled route with current roots; stored policy settings remain closed. See [configuration/runtime](../engineering/configuration-and-runtime.md#private-static-deployment-roots).

The six [recipes](../../config/recipes/) are static candidates generated by `config example --recipe NAME`; no installation or runtime qualification is implied. The split example assigns only sync locally and declares authenticated Control/Ingest/Archive owners. Local plaintext database routes require an explicit loopback/private-bridge boundary; cross-host routes use verify-full. When changing a recipe endpoint to verify-full, explicitly set its TLS mode and remove local_boundary from that endpoint. The absent boundary keeps its schema default instead of inheriting the plaintext recipe exception; an explicit boundary with verify-full is rejected. Selected verify-full dependencies require both ca_file and server_name; validation checks their syntax without opening certificates, reading secrets or contacting servers. Unselected dependencies may stage incomplete TLS settings but still require valid syntax. ClickHouse verify-full also requires an HTTPS endpoint.
