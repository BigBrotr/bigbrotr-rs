## Positive original-request recovery candidate

`recovery.py --root <owned-lab> --run-tag <tag>` uses a clean exact-source build
from `native_initialization.py --producer-recovery`. Its first connected scenario
raises a real PostgreSQL exception after the signed event's native commit, checks
that the original outcome copy rolled back, joins the old Control driver, closes
the native producer under a fresh Control claim, then resolves event and bootstrap
originals. The event copy must name the current recorder; the existing bootstrap
copy and exact retries retain their original row/xmin. Full independently expected
native bytes, original inputs and all Control tables are compared. Source and
artifact checks precede execution. A test program's presence is not PASS evidence;
the checkpoint owns current executed status and remaining failure/process cases.

The extended `--scenario` selector covers native-open/PG-closing refusal,
reservation byte-length/digest/manifest conflicts, reduced decoding resources,
initial cancellation, policy refusal, local expiry, SQL rollback/delay and both
lost-COMMIT orders. Corrupt fixture reservations are changed before insertion by
an explicit lab-only trigger; production guards remain enabled. Engine error logs
are correlated to the original Control backend so a generic Backend error cannot
stand in for the intended copy failure. Every exact retry emits its complete
snapshot, including xmin. A third Control claim follows retryable failures; a
committed-but-undelivered copy retains the second recorder and xmin.
`build_recovery_probe.py` builds only this client in `/out/recovery-probe` from a
separate Git export, requiring all product/dependency inputs equal to d2959da.
`--fixture-build` selects its verified artifact without replacing baseline binaries.
These finite same-process reconnect cases do not qualify fresh-process exclusion,
held native LOCK, complete drain, ACK or successor authority.

The manifest corruption case requires a privileged fixture fault **after** the
ordinary reservation BEFORE guards: migration0011 already rejects a changed
manifest while its existing first reservation is present. The first `manif1`
attempt demonstrates that earlier refusal and is retained as a failed recovery
setup, not as resolver qualification. The corrected fixture changes only request2
immediately before insertion after the guards; subsequent immutability remains
intact, and outcome copying must still refuse. This exercises defensive reading
of corrupted metadata, not an allowed producer write. Actual trigger order and
enabled state are captured; the ordering follows PostgreSQL16's
[CREATE TRIGGER contract](https://www.postgresql.org/docs/16/sql-createtrigger.html).
